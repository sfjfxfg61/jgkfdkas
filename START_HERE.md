# Victoria v11 — установка обновления

Этот архив заменяет исходники бота v10. Старые команды, 4 тарифа, 6 языков, ручной чат, рассылка, статистика, партнёры и учёт комиссий сохранены. Звонки в Black теперь описаны как **доступ к видеозвонкам по предварительному согласованию**: без квоты два звонка и без обещания 20 минут. Бот сохраняет заявку, уведомляет администратора; администратор передаёт её исполнителю и согласует время.

## 1. Перед обновлением

- Сделай резервную копию БД и сохрани старый исходный ZIP.
- Останови старый сервис: один BOT_TOKEN должен обслуживать один polling-процесс.
- На присланном скрине раскрыты секреты. Перевыпусти BOT_TOKEN через BotFather, GROQ_API_KEY и используемый серверный ключ Supabase; обнови значения на Render. В архиве секретов нет. AI-ответы эта версия не запускает.
- Если были реальные оплаченные подписки старой версии: сохрани старый BOT_TOKEN только в `LEGACY_INVOICE_SIGNING_KEY` для проверки уже подтверждённых исторических чеков/продлений. Новые счета с этим ключом не принимаются. Создай новый независимый `INVOICE_SIGNING_KEY`, например `python -c "import secrets; print(secrets.token_hex(32))"`. Сохраняй его при последующих сменах BOT_TOKEN. Старые ещё не оплаченные ссылки нужно создать заново.

## 2. База Supabase

В SQL Editor выполни **V11_SETUP.sql** целиком. Один файл включает создание пустой БД, upgrade присланной схемы, партнёров v10 и новые RPC v11. Старые таблицы, платежи и пользователи не удаляются. Старые холодные цепочки из v10 отменяются; остаётся история. SQL повторно выполняется без удаления данных.

Проверка:

```sql
select public.victoria_v11_preflight();
```

Ожидаемый ответ: `{"ok": true, "version": 11}`. `SUPABASE_KEY` должен быть service_role или sb_secret, не anon. Не запускай только старый V10_MIGRATION_SAFE.sql для этого релиза.

## 3. Render

Загрузи содержимое папки victoria-v11 в репозиторий и задеплой Dockerfile (`python main.py`). В присланных переменных имена совместимы: `PRIVATE_CHANNEL_URL=-100…` и числовые `PUB_LINK_*` поддерживаются. Остальные переменные перенеси из текущего сервиса, с заменёнными секретами.

Для устойчивой работы polling, таймеров и восстановления платежей нужны:

- Постоянно работающий сервис, **не Free**, один экземпляр.
- Persistent Disk с точкой монтирования `/var/data/victoria`, размером 1 GB.
- Новая переменная `STATE_DIR=/var/data/victoria`.
- `FOLLOWUPS_ENABLED=true`, `MARKETING_MODE=limited`, `AUTO_REPLY_AI=false`, `PORT=8080`.

`render.yaml` содержит Starter, один экземпляр и диск. При обновлении существующего сервиса через Git push эти настройки не обязаны примениться автоматически: проверь их в Render Dashboard. Это оплачиваемая конфигурация; архив не меняет твой тариф сам.

`MARKETING_MODE=limited`: текущие ограниченные gate/offer/checkout-напоминания и проверка после покупки. Старый режим всех цепочек сохранён как `legacy`; включается явно. `/stop` позволяет человеку остановить напоминания; `/resume_reminders` включает будущие цепочки снова, не восстанавливая старые отменённые задачи.

Free засыпает после 15 минут без входящего трафика и не поддерживает persistent disk: https://render.com/docs/free . Требования диска: https://render.com/docs/disks . Polling остаётся прежним; переход на webhook сам по себе не запускает фоновые таймеры постоянно.

## 4. Права Telegram

- Администратор должен открыть бота и нажать Start; `ADMIN_ID` — его числовой ID.
- В приватном канале боту нужны права приглашать и ограничивать/удалять участников. Без обоих прав создание новых счетов блокируется.
- В публичных каналах боту нужны права администратора для проверки подписки; при числовых ID — право приглашать.
- Приват должен оставаться закрытым. Оплаченные ссылки создают заявку на вступление, бот проверяет оплату вошедшего. Старые общие инвайты отзови вручную в настройках канала; не публикуй их.
- Служебные администраторы и боты не удаляются обработчиком входа. Неизвестные обычные аккаунты, вошедшие по старым ссылкам, удаляются при получении события. Уже находившиеся в канале неизвестные участники не сканируются автоматически — проверь их список при переходе.

## 5. Проверка после deploy

1. `/diag` от админа: БД, приват invite/restrict и публичные каналы должны быть исправны.
2. С другого аккаунта выбери тариф дважды. Админу должны прийти **два сообщения о выборе**, это ещё не оплата.
3. Проведи одну реальную покупку Stars. Покупателю — подтверждение и кнопка доступа, админу — уведомление об оплате; в `payments` — один charge.
4. По ссылке вступи с аккаунта покупателя; попытка постороннего должна быть отклонена.
5. Проверь `/paysupport` без публичной подписки, обычное сообщение Pro+, отмену/возобновление подписки.
6. Для активного Black: `/call` → уведомление админу → `/calls` → `/call_done ID`. После завершения можно подать новую заявку; лимита двух заявок за период нет. Повторное нажатие до завершения возвращает ту же заявку.
7. `/recovery` показывает незавершённые чеки и очередь уведомлений. Рабочий цикл повторяет их автоматически каждые 30 секунд. Ошибки активации ищи также в логах.

## Что изменено

- Платёжные сообщения обходят лимитер. Чек пишется на диск до обращения к БД и восстанавливается после сбоя/перезапуска при сохранённом диске.
- SQL активирует оплату атомарно и идемпотентно по charge ID. Аналитика не блокирует доступ. Старый initial subscription ID сохраняется при продлении; отмена заменённой подписки хранится в БД и повторяется.
- Если старое продление всё же пришло после смены подписки, оно записывается отдельно, текущий тариф не заменяется; админу приходит запрос на сверку/возврат.
- Уведомления о выборе, оплате, заявках и входящих сообщениях сохраняются перед доставкой. Неуспешная доставка админу повторяется.
- Неудачное удаление из канала не сбрасывает `channel_member`; expiry повторит попытку. Покупка и expiry одного пользователя синхронизированы в одном процессе.
- Поддержка и платные услуги не требуют подписки на публичный канал. Обычные сообщения Pro/Ultra/Black попадают в платный inbox автоматически.
- Перед отправкой напоминания проверяются текущая задача и пользователь. Finish/retry проверяют владельца и время claim. Постоянная ошибка или пятая неудача прекращают retries.
- Неопределённая доставка после падения воркера помечается `failed` для проверки, а не бесконечно отправляется повторно. Новое сообщение пользователя во время ответа админа остаётся в очереди.
- `/health` сообщает состояние фоновых задач и размер очереди восстановления. Это проверка liveness, не доказательство успешной доставки каждого сообщения.

## Пределы проверки

Проверены локальные сценарии с заглушками Telegram и реальный PostgreSQL-движок PGlite. Доступа к твоему действующему Render/Supabase не использовали, реальную оплату не проводили. Поэтому пункт 5 обязателен до расширения трафика.

Уведомления Telegram имеют семантику повторной доставки: редкое падение между успешной отправкой и записью результата может дать дубликат сообщения. Активация доступа и комиссия по тому же charge не удваиваются. При потере самого диска журнал не восстановится — нужны резервные копии диска. Старые платежи без истории entitlement требуют ручной сверки при возврате, чтобы не придумать срок доступа.

Чат и звонки обслуживаются людьми; бот автоматизирует заявки, учёт и уведомления. Контент, доступность исполнителя, сроки обслуживания и реальные условия заполни в TERMS.md/PRIVACY.md перед продажами. Доход код не гарантирует.
